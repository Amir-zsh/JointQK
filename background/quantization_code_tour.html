    Section 1 · Bird's-eye view

    The pipeline — five stages, two parameters

    Before diving into individual functions, the whole compression pipeline. Every method in this tour — TurboQuant, JointQK, QPCA, and any reasonable extension — factors the compression of a key vector $k \in \mathbb{R}^d$ into the same five-stage pipeline. The methods differ in only two of those stages.

    The five stages
    1. Build the basis (offline, per-method) — from $\Sigma_Q$ and $\Sigma_K$ (or just a seed, for TurboQuant), produce a pair of linear maps $F, G \in \mathbb{R}^{d \times d}$ satisfying $F G = I$. Forward $F$ rotates keys into a quantize-friendly basis; inverse $G$ undoes the rotation. Note $F^\top \neq G$ in general — only when $F$ is orthogonal.
    2. Compute the per-coord score (offline, per-method) — assign every coordinate $j$ a non-negative weight $\mathrm{score}_j$ encoding "how much does this coordinate matter to the downstream attention?"
    3. Water-fill the bit budget (offline, shared) — distribute the total $b_\text{avg} \cdot d$ bits across coordinates in log-domain proportion to the score: $B_j \propto \tfrac{1}{2} \log_2 \mathrm{score}_j + \text{const}$, clamped at $B_j \le 8$ and rounded to integers preserving the sum.
    4. Build per-coord Lloyd–Max codebooks (offline, shared) — for each coord, store $2^{B_j}$ centroids of a unit-Gaussian source, scaled by per-coord standard deviation $\sigma_j$. Pad the variable-length codebooks into a single tensor for vectorised lookup.
    5. Round-trip a key (online, shared) — at inference time, for each key vector: $c = k F$, snap each $c_j$ to its codebook's nearest centroid, then $\hat k = c_\text{quant}\, G$.
    Observation 1.1 — Three of five stages are shared

    Stages 3, 4, 5 are identical across all methods. All three route through the same water-fill allocator, the same per-coord Lloyd–Max codebook construction, and the same PerCoordCompressor.roundtrip(). The methods differ only in stages 1 (basis) and 2 (score).

    Why this factoring is useful

    The shared-vs-per-method split isn't a stylistic choice; it is structural. Adding a new method — say, a margin-aware basis with an attention-KL-driven score (companion §9 open question) — means writing one new build_X_basis function. Nothing else changes. The PerCoordCompressor, the water-fill, and the evaluation kernel all stay as-is.

    It also makes the comparison fair: when QPCA wins logit_err and loses top-1 in the experimental table, we know the difference comes from the basis and the score — not from a subtly different quantizer, codebook, or scoring kernel.

    The tour now walks the shared pipeline first (§2 the quantizer, §3 the bit allocator), then each method's basis + score in turn (§4 TurboQuant, §5 JointQK, §6 QPCA), then the shared evaluation kernel (§7), and finally the recap matrix (§8).

    Section 2 · The shared quantizer

    The common abstraction: PerCoordCompressor

    The three methods are identical downstream of this point. They each construct one PerCoordCompressor per (layer, kv-head, bit-width); from there, every scoring metric runs through the same roundtrip(). The interesting differences are entirely in the four tensors the methods feed in.

    Section 3 · The shared bit allocator

    The water-fill rule

    Each method supplies a per-coordinate score. The shared allocate_bits helper turns that score into an integer per-coordinate budget summing to $d \cdot b_\text{avg}$.

    The water-fill formula

    For per-coord variances $\sigma_i^2$ and per-coord bits $B_i$, the high-rate scalar-quantization distortion is $\propto \sigma_i^2 \cdot 2^{-2 B_i}$. Minimising $\sum_i \sigma_i^2 \cdot 2^{-2 B_i}$ subject to $\sum_i B_i = B_\text{tot}$ gives

    $$B_j \;\propto\; \tfrac{1}{2} \log_2 \mathrm{score}_j \;+\; \text{const},$$

    i.e., bits are spent in log-domain proportion to the per-coord score. The score is the only thing each method customises — it encodes "which coordinates does this method think deserve more bits."

    pipelines/calibration/analyze_bases.py:145 
    def allocate_bits(score: Tensor, b_avg: int, max_coord_bits: int = 8) -> Tensor:
    total_bits = b_avg * d

    # 1. Continuous log-domain water-fill on the score
    bits_continuous = water_fill(score, total_bits)            # (..., d), real-valued

    # 2. Largest-remainder rounding that preserves the sum
    bits_int = round_bits_to_integer(bits_continuous, total_bits)

    # 3. Clamp at 8 bits (2^8 = 256 centroids is already near-continuous
    #    for scalar Lloyd–Max on a Gaussian source), redistribute excess
    #    to coords with the lowest current allocation.
    bits_int = clamp_at_max_and_redistribute(bits_int, max_coord_bits)
    return bits_int
    The 8-bit cap

    The cap exists because Lloyd–Max at 8 bits has 256 centroids per coord — already within 0.1% of the continuous-rate limit for a Gaussian source. Past that, extra bits buy nothing for the scalar quantizer. The "redistribute to lowest-bit coords" step preserves the total budget when some coord wants to be allocated 10 bits but is capped at 8.

    Section 4 · Method 1

    TurboQuant — random orthogonal basis, uniform bits

    TurboQuant (called v3 internally for historical reasons) is the calibration-free baseline. The basis is a random Haar-uniform orthogonal matrix; bits are spent uniformly. Justified by concentration of measure: in a random basis, every coord is near-Gaussian with variance $\mathrm{tr}(\Sigma_K)/d$, where scalar Lloyd–Max is near-optimal.

    Step 1 — Build the basis

    notebook cell 7 · build_turbo_basis 
    G = torch.randn((L, H, d, d), generator=gen)            # i.i.d. Gaussian
Q_orth, R = torch.linalg.qr(G)                          # QR factorisation

# Sign-fix the columns so the QR convention is platform-deterministic.
# (Without this, the basis flips sign with platform / seed.)
signs = torch.sign(torch.diagonal(R, -2, -1)).clamp_min(0) * 2 - 1
forward = Q_orth * signs.unsqueeze(-2)                    # (L, H, d, d) orthogonal
inverse = forward.transpose(-1, -2)                      # orthogonal: inv = R^T

    Step 2 — Per-coord std and uniform score

    same cell 
    rotated     = inverse @ sigma_k @ forward               # Σ_K in the random basis
k_diag_rot  = rotated.diagonal(-2, -1).clamp_min(1e-30)
score       = torch.ones_like(k_diag_rot)               # UNIFORM allocation
std         = k_diag_rot.sqrt()                         # for Lloyd–Max codebook
    Why uniform bits, and where Σ_K enters

    Under concentration of measure, a random orthogonal rotation makes every coord of $R^\top \Sigma_K R$ have variance roughly $\mathrm{tr}(\Sigma_K)/d$. There's no anisotropy to exploit, so uniform allocation is the right call. Σ_K is used only to scale the Lloyd–Max codebook (std_per_coord) — the basis itself is data-independent. That's why TurboQuant ships without calibration files.

    Section 5 · Method 2

    JointQK — symmetrised Q–K eigenbasis, logit-variance bits

    JointQK builds an orthogonal basis from the symmetrised cross-product $(\Sigma_Q \Sigma_K + \Sigma_K \Sigma_Q)/2$, then water-fills bits using a per-coord logit-variance proxy. This is the current production K-side basis.

    Step 1 — Build the basis

    pipelines/calibration/analyze_bases.py:127 
    def jointqk_basis(sigma_q, sigma_k, eps):
    sq = regularize_batch(sigma_q, eps)              # add ε·(tr/d)·I  for PSD insurance
    sk = regularize_batch(sigma_k, eps)
    sym = 0.5 * (sq @ sk + (sq @ sk).transpose(-1, -2))   # symmetrise Σ_Q Σ_K
    vals, vecs = torch.linalg.eigh(sym)              # real eigenpairs
    return vecs_sorted_by_descending_eigvalue              # (L, H, d, d) orthogonal
    Three subtleties

    (1) Regularize. Empirical covariances from small bundles can be near-singular. regularize_batch adds $\varepsilon \cdot \mathrm{tr}(\cdot)/d \cdot I$ — shifts the spectrum up by a few percent of the average eigenvalue. Enough to make eigh stable; tiny enough to not perturb the result.

    (2) Symmetrise. A product of two symmetric matrices is generally not symmetric (it would be only if they commute). The symmetrised average $(\Sigma_Q \Sigma_K + \Sigma_K \Sigma_Q)/2$ has real eigenvalues and orthogonal eigenvectors — required for the orthogonal-basis story.

    (3) Sort descending. By convention, the "top" coordinates correspond to the largest eigenvalues — the directions where the Q–K product is largest. The water-fill will hand them more bits.

    Step 2 — Per-coord score and std

    notebook cell 9 · build_jointqk_basis 
    R = jointqk_basis(sigma_q, sigma_k, eps)
forward = R
inverse = R.transpose(-1, -2)                            # orthogonal → inv = R^T

# Q variance per coord IN R-basis
q_diag = (inverse @ regularize_batch(sigma_q, eps) @ forward).diagonal(-2, -1)
# K variance per coord IN R-basis
k_diag = (inverse @ regularize_batch(sigma_k, eps) @ forward).diagonal(-2, -1)

score = q_diag * k_diag                                  # logit-variance proxy
std   = k_diag.sqrt()                                    # for Lloyd–Max
    Why score = $q\_\text{diag}_i \cdot k\_\text{diag}_i$

    In the orthogonal $R$-basis, write $q_R := R^\top q$ and $k_R := R^\top k$. Under a queries–keys independence approximation, the per-coord contribution to logit variance factorises:

    $$\mathrm{Var}\!\bigl( q_R^{(i)} \cdot k_R^{(i)} \bigr) \;=\; \underbrace{(R^\top \Sigma_Q R)_{ii}}_{q\_\text{diag}_i} \;\cdot\; \underbrace{(R^\top \Sigma_K R)_{ii}}_{k\_\text{diag}_i}.$$

    So water-fill on this product allocates more bits to coordinates that carry more of the logit's variability — coords that decide which key wins the argmax.

    The water-fill concentrates bits on the high-$q\_\text{diag} \cdot k\_\text{diag}$ tail (a handful of coords get 5–8 bits) at the cost of starving low-leverage coords (51 coords get only 2 bits).

    Section 6 · Method 3

    QPCA — non-orthogonal basis, eigenvalue-water-fill

    QPCA is the closed-form optimum of the all-pairs MSE objective (companion §1–§6). Its forward map is non-orthogonal in the Euclidean sense — it's $M_q$-orthonormal. The bit-allocation score is the eigenvalues $\Lambda$ alone, because the Q-weighting is already absorbed into the basis (companion Remark 6.4).

    Step 1 — Cast to fp64

    notebook cell 11 · build_qpca_basis 
    sq = regularize_batch(sigma_q, eps).to(torch.float64)
sk = regularize_batch(sigma_k, eps).to(torch.float64)
    Why fp64

    $M_q^{-1/2}$ amplifies condition number. fp32 loses too many digits, especially in layer 0 where attention sinks make $\Sigma_Q$ near rank-deficient. Compute in fp64, cast back at the end.

    Step 2 — Spectral square roots of $M_q$

    same cell 
    q_vals, q_vecs = torch.linalg.eigh(sq)               # M_q = U·diag(σ_i)·U^T
q_vals = q_vals.clamp_min(eps)                       # numerical safety

Mq_half     = _sym(q_vecs @ torch.diag_embed(q_vals.sqrt())  @ q_vecs.transpose(-1, -2))
Mq_neg_half = _sym(q_vecs @ torch.diag_embed(q_vals.rsqrt()) @ q_vecs.transpose(-1, -2))

    Spectral construction: $M_q^{1/2} := U \operatorname{diag}(\sqrt{\sigma_i}) U^\top$ from the eigendecomposition $M_q = U \operatorname{diag}(\sigma_i) U^\top$. Same trick for $M_q^{-1/2}$ with rsqrt. _sym kills tiny asymmetric numerical noise.

    Step 3 — Form $A$ and eigendecompose

    same cell 
    A = _sym(Mq_half @ sk @ Mq_half)                     # A = M_q^{1/2} Σ_K M_q^{1/2}
lam, V = torch.linalg.eigh(A)                        # A = V·Λ·V^T,  V orthogonal
order  = torch.argsort(lam, descending=True)
lam = lam[order];  V = V[..., order]                 # sort descending

    $A$ is the central matrix of the QPCA derivation — the congruence transform of $\Sigma_K$ by $M_q^{1/2}$, i.e., "$\Sigma_K$ viewed in the Q-weighted metric." Its eigenvalues $\Lambda$ are the per-coord code variances.

    Step 4 — Forward and inverse (the non-orthogonal part)

    same cell 
    forward = (Mq_half @ V).float()                      # applied as: k @ F
inverse = (V.transpose(-1, -2) @ Mq_neg_half).float()    # applied as: r @ G
    F and G are inverses, but F is not orthogonal

    The two maps compose to the identity:

    $$F\,G \;=\; M_q^{1/2} V \cdot V^\top M_q^{-1/2} \;=\; M_q^{1/2} M_q^{-1/2} \;=\; I.$$

    But $F$ is not orthogonal in the Euclidean sense: $F^\top F = V^\top M_q V \neq I$ in general. Instead, the column-vector decoder $U^* := M_q^{-1/2} V$ is $M_q$-orthonormal:

    $$U^{*\top} M_q U^* \;=\; V^\top M_q^{-1/2} M_q M_q^{-1/2} V \;=\; V^\top V \;=\; I.$$

    The notebook's sanity prints confirm this:

    printed by notebook cell 11 
    QPCA   ||F @ G - I||_F  ≈ 1.9e-6     # inverses, OK
       ||F^T F - I||_F  ≈ 4e+0       # non-orthogonal — confirms the math

    Step 5 — Score and std

    same cell 
    score = lam                                          # Λ alone — Q-weight is already in F
std   = lam.sqrt()                                   # for Lloyd–Max
    Why the score is $\Lambda$ alone

    By the clean property (companion Remark 6.4), in the QPCA basis the Q-weighted key MSE equals the plain Euclidean code MSE:

    $$(\hat k - k)^\top M_q (\hat k - k) \;=\; \|\eta\|_2^2 \;=\; \sum_i \mathrm{Var}(\eta_i).$$

    Each code coord contributes equally to the loss. With per-coord noise $\propto \lambda_i \cdot 2^{-2 B_i}$, the optimal allocation is water-fill on $\lambda_i$ alone — no further Q-weighting needed.

    Step 6 — Quantization

    The same PerCoordCompressor.roundtrip as before, with the (non-orthogonal) QPCA maps:

    conceptual 
    # c = k @ (M_q^{1/2} V)            forward — rotate by V *then* scale by M_q^{1/2}
# c_quant[:, j] = nearest in Lloyd–Max codebook scaled by std[j] = sqrt(λ_j)
# k_hat = c_quant @ (V^T M_q^{-1/2})   inverse — scale by M_q^{-1/2} then de-rotate

    The round-trip is an oblique projection (companion §4): $\hat k = M_q^{-1/2} V V^\top M_q^{1/2} k = k$ in the no-quantization limit, but along an oblique axis when quantization noise is present.

    Section 7 · Shared evaluation kernel

    How the four metrics are computed

    The kernel is identical across all three methods. For each example and each (layer, kv-head) we compute $k\_\text{mse}$, $\mathrm{logit\_err}$, top-1, and top-5 retention against the original keys. Four implementation tricks make this fast.

    Setup per (l, h) — done once

    notebook cell 15 · score_example 
    k = k_all[l, h, :T, :].float()                              # (T, d) — original keys
q = q_all[l, h*group_size:(h+1)*group_size, :T, :].float() \
        .reshape(-1, d)                                    # (4T, d) — GQA-pooled queries
qq          = q.transpose(0, 1) @ q                          # (d, d) — query Gram
k_t         = k.transpose(0, 1)                              # (d, T)

# Hoisted out of the (method, bits) inner loop — identical for all 9 combinations.
real_logits = q @ k_t                                       # (4T, T)
real_top    = real_logits.argmax(dim=-1)                    # (4T,)
n_q         = int(real_top.numel())
    Trick 1 — Hoist what doesn't depend on (method, bits)

    The original code recomputed real_logits and real_top inside the inner loop — 9 times per (l, h) per example. Pulling them out cut per-example time by ~3×, the difference between hitting the 600 s nbconvert timeout and finishing in 8 minutes.

    Inner loop — per (method, bits)

    same cell 
    for method, comps_bits in comps_by_method.items():
    for bits in k_bits_list:
        comp = comps_bits[bits][(l, h)]
        k_hat = comp.roundtrip(k).float()                   # ←── QUANTIZE HERE
        err = k - k_hat
        acc = accums[method][bits][l]

        # (1) k_mse — unweighted reconstruction error
        acc['mse_num'] += float(err.square().sum().item())
        acc['mse_den'] += int(err.numel())

        # (2) logit_err — Q-weighted key MSE via trace identity
        ee = err.transpose(0, 1) @ err                       # (d, d)
        acc['logit_num'] += float((qq * ee).sum().item())     # elem-mul + sum = trace
        acc['logit_den'] += int(q.shape[0] * T * T)

        # (3,4) top-1 / top-5 retention
        approx_logits = q @ k_hat.transpose(0, 1)             # (4T, T)
        approx_top    = approx_logits.argmax(dim=-1)
        top1 = int((real_top == approx_top).sum().item())
        approx_top5 = approx_logits.topk(5, dim=-1).indices
        top5 = int((approx_top5 == real_top.unsqueeze(-1)).any(-1).sum().item())

        acc['top1_num'] += top1;  acc['top1_den'] += n_q
        acc['top5_num'] += top5;  acc['top5_den'] += n_q
    Trick 2 — The trace identity for logit_err

    By definition, $\mathrm{logit\_err} = \sum_{i, j} (q_i^\top \delta_j)^2$ where $\delta_j = k_j - \hat k_j$. Rearrange the sum:

    $$\sum_{i, j} (q_i^\top \delta_j)^2 \;=\; \sum_j \delta_j^\top \!\left(\sum_i q_i q_i^\top\right)\! \delta_j \;=\; \mathrm{tr}\!\bigl(qq \cdot \mathrm{ee}\bigr),$$

    where $\mathrm{ee} := \sum_j \delta_j \delta_j^\top = \mathrm{err}^\top \mathrm{err}$. The trace of a product of two matrices equals the Frobenius inner product, which is element-wise multiplication plus sum: (qq * ee).sum(). This avoids forming an explicit $(T, d, d)$ intermediate.

    Trick 3 — GQA pooling

    Qwen3-8B has 32 Q-heads sharing 8 KV-heads (group size 4). For each kv-head $h$, four Q-heads see the same compressed K. The notebook reshapes the four Q-heads into a single $(4T, d)$ query block, so a single matmul produces all four heads' logits at once.

    Trick 4 — int() instead of float() for counts

    Top-1 / top-5 counts are integers; using (real_top == approx_top).sum().item() with an int cast avoids an extra float conversion and reduces host-device sync overhead in the inner loop. Minor but compounds over 3 examples × 36 layers × 8 heads × 9 (method, bits).

    Finalization — pool across layers, divide

    notebook cell 15 · finalize 
    for bits in by_bits:
    layers = [l for l in by_layer if not (exclude_layer_0 and l == 0)]
    out[method][bits] = {
        'k_mse':     sum(mse_num for l)   / sum(mse_den for l),
        'logit_err': sum(logit_num for l) / sum(logit_den for l),
        'top1':      sum(top1_num for l)  / sum(top1_den for l),
        'top5':      sum(top5_num for l)  / sum(top5_den for l),
    }

    Layer 0 is excluded because of its anomalous attention-sink behaviour at the position-0 token (a project-wide convention; see CLAUDE.md).

    Section 8 · Recap

    The three-method matrix

    Every method routes through the same PerCoordCompressor.roundtrip; every metric is computed by the same kernel. The differences are upstream — how the forward map is built, and what score is fed to the water-fill bit allocator.

    per-coord std $\sqrt{\mathrm{diag}(R^\top \Sigma_K R)}$ $\sqrt{\mathrm{diag}(R^\top \Sigma_K R)}$ $\sqrt{\lambda_i}$
    needs $\Sigma_Q$? no — calibration-free yes yes (also $M_q^{-1/2}$)
    basis-build cost one QR per (L, h) one $\mathtt{eigh}$ per (L, h) three $\mathtt{eigh}$ per (L, h) (fp64)

# 2. Water-fill bits at target budget

    Where the math becomes code

    Each method's mathematical character — what it considers "the right basis" and "the right bits-per-coord weighting" — lives entirely in the four fields of the basis dict. From allocate_bits onward, the three methods are indistinguishable to the compressor.

    That separation is why adding a new method (margin-aware bases; attention-KL-driven allocation; etc., per companion §9's open questions) is a single new build_X_basis function and a single line in the method registry — no changes to the compressor or the scoring kernel.
