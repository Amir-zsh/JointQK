1. The problem, in bytes

Why any of this exists. All figures for gpt-oss-20B at 128K context, batch 1.

Every token the model reads leaves behind a key vector and a value vector per layer, per KV head. gpt-oss-20B has 24 layers, but they alternate: 12 are sliding-window layers that only ever see the last 128 tokens, and 12 are full-attention layers that see everything. Only the full-attention layers accumulate a cache worth compressing — and only those 12 are touched by any of this.

\[ \underbrace{64\times 2\,\text{B}}_{K}\;+\;\underbrace{64\times 2\,\text{B}}_{V} \;=\; 256\ \text{B} \quad\text{per token, per layer, per KV head} \] \[ 256\,\text{B}\times\underbrace{8}_{\text{KV heads}}\times\underbrace{12}_{\text{full-attn layers}} \times\underbrace{131{,}072}_{\text{tokens}}\;=\;\mathbf{3.00\ GB} \]

head_dim = 64. On a 40 GB card, for a single request. Under TP=2 each rank holds half of this (4 KV heads).

2. Three bands, one address space

The cache is not uniform. Understanding the slot-id namespace is the key to understanding everything else.

Nothing quantizes the whole sequence. The pool keeps two high-precision (HP) bands in bf16 and compresses only what is between them:

  • prefix the first P = 64 tokens — the attention sinks and prompt anchors, which attention returns to constantly;
  • quantized everything in the middle;
  • recent the most recent R = 256 tokens, which decode is most sensitive to.

This has an immediate consequence that explains several otherwise-confusing measurements: a prompt shorter than P + R = 320 tokens never touches the quantized tier at all and is served entirely from bf16.

The geometry constants, and where they come from

One constant drives the whole layout. N_Q is the number of quantized slots that fit in the byte footprint of a single high-precision token — since INT2 packs 4 coordinates per byte and bf16 uses 2 bytes per coordinate, that ratio is exactly 4x2 = 8:

\[ N_Q \;=\; 4\cdot\operatorname{sizeof}(\texttt{hp\_dtype}) \;=\; 8 \quad\text{(bf16)} \] \[ \begin{aligned} \operatorname{HP\_OFFSET} &= \texttt{num\_quant\_pages}\cdot N_Q &&= 5251\times 8 = 42{,}008\\ \text{recent ring} &= R + N_Q &&= 256 + 8 = 264\ \text{slots/request}\\ \text{flush interval} &= N_Q &&= 8\ \text{tokens/page} \end{aligned} \]

compute_page_geometry, unified_kv_pool.py:110-127. The startup log prints this ring formula as "R + N_Q-1"; that string is stale — the code adds a full N_Q.

N_Q is simultaneously the allocator page size, the engine's --page-size, and the flush batch size. P and R are both required to be multiples of it. The recent ring is deliberately one page larger than R so that a decode step can reserve its next slot before the flush plan releases the oldest page, without the two aliasing.

Deployed vs library defaults

The engine's own defaults are P=32, R=128 (environ.py:215-216). The serve script overrides them to P=64, R=256. Everything in this document uses the deployed values.

Who owns a slot? Three different allocation disciplines

In a stock bf16 server there is one flat pool and a single free list: every request takes whatever slot is free next. Here the three regions behave differently, and only one of them is statically partitioned.

RegionshareDisciplineHow a slot is obtained
quant80.3% dynamic, shared Paged free list (free_pages), pages of N_Q=8. Any request draws any free page; freed pages return to the same list. This is ordinary paged allocation — just at page granularity 8 instead of 1.
HP-prefix15.7% dynamic, shared Its own paged free list (hp_prefix_free_pages). The allocator takes req_pool_indices only to drive iteration order — the allocation itself is pooled, so any request can get any free page.
HP-recent4.0% static, private Not allocated at all. Request slot i permanently owns a 264-slot ring at i×264 + base, advanced by a per-request cursor. No free list, no search.

The static ring is a deliberate trade. Every decode step must write one HP-recent slot and every eighth step must demote the oldest page — putting that on a free list would mean an allocation and a lookup on the hottest path in the engine. Making it pure arithmetic keeps the decode step sync-free and shape-static, which is what allows the whole thing to be captured in a CUDA graph. The cost is 264 × max_req_slots = 2,112 slots reserved whether or not the requests exist — 4% of the pool.

Can two requests share the same physical slot?

Not in this deployment. The pools are "shared" only in the sense that the free lists are common — at any moment each slot belongs to exactly one request. True sharing (two requests whose identical prompt prefix points at the same KV rows) is what a radix prefix cache does, and the served configuration runs with --disable-radix-cache. HP-recent could not be shared in any case, since it is carved by request index.

So: capacity is fixed at startup — all three arenas are allocated once, sized from max_total_num_tokens and max_running_requests, and never grow. Placement is dynamic for 96% of the slots and static for the 4% that decode touches every single step.

4. Path A — scalar INT2

The published OSCAR baseline. Each coordinate is rounded independently to one of four levels, with one shared scale for the whole head.

The encode pipeline

\[ \tilde k = k R_k \qquad\text{($R_k$ orthonormal $64\times64$, per layer)} \] \[ \tau=\operatorname{sort}\bigl(|\tilde k|\bigr)_{\lfloor 0.96\cdot 64\rfloor}, \qquad \tilde k \leftarrow \operatorname{clamp}(\tilde k,\,-\tau,\,+\tau) \] \[ s=\frac{\max\tilde k-\min\tilde k}{3}, \qquad z=\frac{-\min\tilde k}{s}, \qquad q=\Bigl\lfloor \tfrac{\tilde k}{s}+z+\tfrac12 \Bigr\rfloor \in\{0,1,2,3\} \] \[ \texttt{packed}=q_0\;|\;(q_1\!\ll\!2)\;|\;(q_2\!\ll\!4)\;|\;(q_3\!\ll\!6) \]

Result: 16 bytes + one (scale, zero) pair. The denominator 3 is \(2^2-1\), the largest representable code.

Reconstruction is

\[ \hat x=(q-z)\,s \]

The endpoints are exact: \(q=0\) returns \(\min\) and \(q=3\) returns \(\max\). The scheme is affine/asymmetric — the four levels are evenly spaced, but the grid is not centred on zero and zero is generally not representable. Note also that \(z\) is stored as a float, not an integer, so no rounding of the zero-point occurs.

The clip, and why it exists

Before computing min/max, each row is symmetrically clipped at the floor(ratio × head_dim)-th order statistic of |row| — deployed at 0.96 for K and 0.92 for V. With only four levels, a single outlier coordinate would stretch (max-min) and coarsen the step for all 64 coordinates. Clipping trades a large error on a few outliers for a smaller error everywhere else. It is implemented as a bisection search inside the kernel (gpu_flush_int2.py:204-226), not a sort.

The basis: deliberately flattening the spectrum

This is the design decision that makes a single shared scale defensible. The K rotation (qqt_r_h_pbr) is orthonormal and ends in a Hadamard-style mixing stage. Measured on the shipped artifact for layer 1:

\[ \frac{\lambda_{\max}}{\lambda_{\min}}\Bigl(\Sigma_K\Bigr)=\mathbf{54.6} \qquad (\lambda\in[0.397,\;21.67]) \] \[ \overline{|R_{ij}|}=0.102 \;\approx\; \tfrac{1}{\sqrt{64}}=0.125 \qquad\text{(dense, near-uniform $\Rightarrow$ energy spreading)} \] \[ \operatorname{diag}\bigl(R^{\top}\Sigma_K R\bigr)\;\longrightarrow\; \text{flat at } \overline{\lambda}=2.41 \]

Measured on the shipped artifact, layer 1. A Hadamard \(H\) satisfies \(\sum_j H_{ij}^2\lambda_j=\overline{\lambda}\) for every row \(i\) — every coordinate ends up with the same variance.

Because a scalar quantizer with one shared scale can only be efficient if every coordinate has comparable variance, INT2's basis is chosen to destroy the anisotropy in the data. That is a coherent design — but it also means INT2 must spend the same 2 bits on every direction, whether that direction matters to the queries or not. Section 5 takes the opposite approach.

5. Path B — group vector quantization

Instead of rounding each coordinate independently, look up a whole 4-dimensional sub-vector in a learned codebook. Same 2 bits per coordinate.

The encode pipeline

\[ r=(k-\mu)F \qquad \begin{aligned} &\mu:\ \text{per-(layer, head) mean, fp32}\\ &F:\ \text{QPCA basis, }64\times64\text{ fp64, \textbf{not} orthonormal} \end{aligned} \] \[ s=\operatorname{RMS}(r)=\sqrt{\tfrac{1}{64}\textstyle\sum_{d} r_d^2}, \qquad r_n=\frac{r}{s} \qquad\text{(one scalar per token, per head)} \] \[ \operatorname{idx}_g=\arg\max_{c\,\in\,\mathcal{C}_g} \Bigl(\langle c,\;r_n[g]\rangle-\tfrac12\lVert c\rVert^2\Bigr), \qquad g=1\ldots16 \]

That argmax is exactly \(\arg\min_c\lVert r_n[g]-c\rVert^2\) with the constant \(\lVert r_n\rVert^2\) dropped. Result: 16 uint8 indices + 1 RMS scale.

The query is mapped by the inverse transpose, which makes the stored dot product reproduce the true one up to a constant:

\[ q_m=q\,F^{-\top} \qquad\Longrightarrow\qquad q_m\cdot r \;=\; q\cdot(k-\mu) \;=\; q\cdot k \;-\; \underbrace{q\cdot\mu}_{\displaystyle c} \]

c is constant across all real keys for a given query, hence softmax-invariant — unless the denominator contains something that is not a real key (§9).

The basis is not a rotation

Unlike INT2's R_k, the VQ forward matrix is not orthonormal — measured on the shipped artifact, F Fᵀ - I has max magnitude 309 and F has condition number 16.8. It is a ΣQ-whitened (QPCA) basis: F = Σ_Q½ V. Only invertibility is needed — F @ inverse = I to 4.4e-15 — because the query is mapped by F⁻ᵀ rather than by F. This is why the general claim "the rotation is orthogonal so q·k is preserved" applies to the INT2 arm only.

The codebook is model state, paid once — not per token.

How it was trained

Calibration ran 4 sequences × 131,072 tokens of concatenated GPQA text through the model, hooking only the full-attention layers and pooling every 4th token's post-RoPE key. Then, for each of the 96 (layer, head) cells independently:

  1. Build the QPCA basis from the accumulated second moments: F = Σ_Q½V, eigendecomposition in float64.
  2. Stratified grouping: the coordinate of eigen-rank r is assigned to group r mod 16. So each 4-dim group deliberately spans the whole eigenvalue spectrum — one high-variance direction paired with progressively lower-variance ones. The permutation is folded into F's columns at training time, so no runtime permutation exists.
  3. Per-token RMS normalise the residuals.
  4. Run 16 independent k-means (batched Lloyd, 25 iterations, empty clusters reseeded from the farthest points), K=256 each.

That is 1,536 k-means fits for one model. Flat allocation: every group gets the same 8 bits.

How the codebook is stored for the decode kernel

At load, the fp16 centroids are cast to fp8-e5m2 and the four bytes of each 4-dim codeword are packed into a single int32, little-endian (coordinate i → byte i). The decode kernel then fetches one whole codeword per 32-bit load and bit-casts the four bytes back to fp16 planes. E5M2 specifically, because that is the only fp8 format Triton can bitcast on sm80.

cb_packed : int32 [12, 8, 16, 256] [layer, head, group, code] kernel: cw = cb_packed[h, g, idx] p0 = bitcast_fp8e5(cw & 0xFF) → fp16 coord 0 p1 = bitcast_fp8e5(cw >> 8 & 0xFF) → fp16 coord 1 p2 = bitcast_fp8e5(cw >> 16 & 0xFF) → fp16 coord 2 p3 = bitcast_fp8e5(cw >> 24 & 0xFF) → fp16 coord 3

The per-token RMS scale is not applied to the reconstructed vector. It is folded into the score column instead, exploiting q · (c·s) = (q · c) · s, which keeps the tensor-core dot product in raw-codeword space:

qk = tl.dot(q_main, tl.trans(kg))     # [BLOCK_H, BLOCK_N] fp32
qk = qk * k_scale[None, :]            # fold ptn scale into the column
qk *= sm_scale

6. Same 8 bits, different points

The cleanest statement of what separates the two methods — and it is not the bit budget.

Take one 4-dimensional group. Both methods spend exactly 8 bits on it:

Scalar INT2

2 bits × 4 coordinates. Each coordinate independently picks one of 4 levels, from a grid set by one scale shared across the entire 64-dim head.

4⁴ = 256 representable points

Group VQ

One 8-bit index into a codebook of 256 centroids, fitted by k-means to this specific (layer, head, group)'s actual residual distribution.

2⁸ = 256 representable points

Identical bit count. Identical number of representable points. The only difference is where those 256 points sit: INT2's are locked to a rectangular lattice with axis-aligned spacing, VQ's are placed wherever the calibration data actually lies.

Why that matters here: the groups are extremely anisotropic

Recall from §5 that stratified grouping deliberately pairs a high-eigenvalue direction with low-eigenvalue ones inside every group. Measured on the shipped codebook, layer 1 head 0, group 0:

\[ \frac{\sigma(\text{coord }0)}{\sigma(\text{coord }1)} =\frac{6.763}{0.461}=\mathbf{14.7\times} \qquad\text{within a single 4-dim group} \] \[ \frac{\sigma_{\max}}{\sigma_{\min}}\Bigl(\text{all 64 coords of the head}\Bigr)=\mathbf{91\times} \]

Measured from the shipped codebook, layer 1 head 0. Compare §4: INT2's basis drives this ratio toward 1 on purpose.

A vector quantizer handles this for free — it simply places more centroids along the wide axis and fewer along the narrow one, because k-means minimises error in the joint space. A scalar quantizer with one shared scale cannot: it must pick a single step size and apply it to every axis. That is precisely why INT2 rotates into a flattened basis first (§4) and VQ rotates into a concentrated one.

What this figure does and does not prove

It shows why a vector quantizer can exploit structure a shared-scale scalar quantizer must first destroy. It does not establish that basis anisotropy is the cause of INT2's failure on gpt-oss — report 14's engine-free simulation found INT2's logit damage is ~3.4× Llama's in every basis tested, including no rotation at all. The honest reading is that these are two coherent designs with different failure modes, and gpt-oss happens to fall outside what the scalar one tolerates.

7. How a token ages into the quantized tier

Nothing is quantized at write time during decode. Compression happens later, in batches of 8.

Every decode step writes its new token to the HP-recent ring in bf16 — always, unconditionally. Only when the ring has advanced a full page does a batch of the oldest tokens get demoted into the compressed tier. A per-request counter tracks this, so a flush happens on exactly one decode step in every N_Q = 8.

The VQ flush is torch-side rather than a Triton kernel: it gathers the HP residual rows for all 12 layers at once with a single index_select, encodes them in chunks of 8 tokens (bounding the [L, c, H, NG, K] score tensor), and scatters indices and scales back. The INT2 flush kernel still runs alongside it to handle V and the req_to_token remap, with its K-packing stage disabled via a K_VQ constexpr.

8. Reading it back

Prefill and decode reconstruct the cache in completely different ways, for good reasons.

The tier split itself is two small Triton kernels: one counts each request's HP slots directly from req_to_token, the host builds the indptr arrays with a cumsum (no device-to-host sync), and a second kernel scatters the two compact index lists. HP indices are rebased to slot - HP_OFFSET; quant indices are stored raw. Note the boundary test is >=, not > — HP slot 0 is valid, and using > would read out of bounds from the quant buffer.

9. The learned sink, and the bug it caused

Why mean-centering — mathematically harmless everywhere else — broke on gpt-oss specifically.

gpt-oss adds a learned per-head sink logit s to the softmax denominator. It has no value vector; it just lets a head attend to "nothing":

\[ \ell_i=\alpha\,q^{\top}k_i, \qquad \text{output}=\frac{\sum_i e^{\ell_i}\,v_i} {\sum_i e^{\ell_i}\;+\;\underbrace{e^{s}}_{\text{sink}}} \]

The sink appears in the denominator only — it has no value vector in the numerator. It controls how much probability mass is withheld from the real tokens.

Recall from §5 that VQ stores a mean-centred residual, which shifts every real-key logit by the same query-dependent constant c = α·q·μ. A softmax over real keys alone is invariant to that. But with a sink in the denominator, it is not:

Written out, with \(c=\alpha\,q^{\top}\mu\) the mean-centering shift:

\[ Z_{\text{old}}=\sum_i e^{\ell_i-c}+e^{s} \;=\;e^{-c}\Bigl(\sum_i e^{\ell_i}+e^{\,s+c}\Bigr) \quad\Longrightarrow\quad \text{sink silently becomes } s+c \] \[ Z_{\text{fixed}}=\sum_i e^{\ell_i-c}+e^{\,s-c} \;=\;e^{-c}\Bigl(\sum_i e^{\ell_i}+e^{s}\Bigr) \quad\Longrightarrow\quad \frac{e^{-c}N}{e^{-c}Z}=\frac{N}{Z}\ \checkmark \] \[ \boxed{\,s'=s-\alpha\,q^{\top}\mu\,} \]

The \(e^{-c}\) factor cancels between numerator and denominator, so the corrected form is exactly equivalent to the original attention.

It is applied in both paths. Decode folds it into the existing stage-2 reducer, so it costs no extra kernel launch (measured: +3.3µs on the reducer, ~0.04 ms across all 12 layers per decode step). Prefill computes the shifted sinks on the torch side, then applies the exact correction to a sink-less FlashAttention output:

\[ o \;\leftarrow\; o\cdot\frac{Z}{Z+e^{s'}} \;=\; o\cdot\sigma\bigl(\log Z-s'\bigr) \]

FlashAttention already returns \(\log Z\) as its LSE, so this is one sigmoid and one multiply — no need to trust the varlen kernel's own sink support, which is untested on sm80.

The old behaviour can still be reproduced deliberately with SGLANG_VQ_DISABLE_SINK_CORRECTION=1. Two asserts guard the corrected path: it is incompatible with nonlinear logit capping and with XAI temperature scaling.
