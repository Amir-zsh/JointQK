KV-cache compression · Report 14

Why OSCAR INT2 fails on gpt-oss-20B

Two independent failures: a scalar-INT2 fidelity limitation and a now-fixed piecewise-prefill engine bug shared by INT2 and vq2.

models unsloth/gpt-oss-20b-BF16 · meta-llama/Llama-3.1-8B-Instruct (reference)
engine vendored OSCAR sglang fork, branch vq2-longhorizon · TP=2 · A100-40GB
date 2026-07-24–25

Verdict

Wiring quantized KV into gpt-oss produced a server that boots and decodes but scores 0.0 on NIAH-8K under INT2, against 88.4 for bf16 on identical rows. Generations are degenerate — every row runs to the token cap emitting word salad.

The finite scalar-INT2 quality collapse reproduces in pure HuggingFace with zero engine code, while the identical simulation leaves Llama untouched at 10/10. That result remains a method limitation.

A second, independent failure was an engine bug: sampled concurrent serving under INT2 or vq2 produced non-finite logits because piecewise graph replay padded query tensors without extending the quantized prefill metadata. The production fix makes the padding a valid isolated sequence and keeps both bulk chunks and ragged tails graphed.

01Background

Transformer inference caches a key and value vector for every token it reads. At long context that cache dominates memory and bandwidth — a 128K prompt costs tens of gigabytes in bf16, and decode speed is bound by streaming it.

This project compresses the key side to roughly 2 bits per coordinate. The pipeline calibrates per-(layer, kv_head) second moments from a small prompt corpus, chooses a per-layer orthogonal basis from those statistics so key energy concentrates in fewer coordinates, quantizes each coordinate independently in that basis, and decompresses on the fly when future queries arrive.

Because the rotation is orthogonal, q·k is preserved: the query is rotated by the same matrix and attention scores are unchanged. All the loss comes from the quantizer.

The two arms

OSCAR INT2 is the published baseline — the authors' production method, vendored from their fork. Keys and values are quantized to 2 bits by per-token affine min-max in the calibrated basis, plus an optional per-row clip. With one scale group per head, a token's 64 coordinates share a single scale and zero-point: four representable levels.

vq2 is our method: the key tier is replaced by a group vector-quantizer with an fp8 codebook learned from the same corpus. The value tier stays on OSCAR's INT2 path unchanged, so the arms differ only in how keys are encoded.

The mixed HP+INT2 cache

Neither method quantizes everything. The pool keeps a high-precision band in bf16 — the first 64 tokens (attention sinks) and the most recent 256 — and quantizes only the middle, flushing aged tokens into the quantized tier in 8-token pages.

This matters throughout: a prompt shorter than ~320 tokens never touches the quantized tier and is served entirely from bf16.

Where the work stood

The method was validated on dense models — Llama-3.1-8B scores 84.3 (INT2) and 92.3 (vq2) on NIAH-8K against a bf16 ceiling of 98.2; Qwen3-8B INT2 reaches 97.6. The task was extending both arms to a much stranger model.

02How gpt-oss-20B is different

gpt-oss is not a scaled-up Llama. Four architectural properties separate it from every model this stack had served, and each required new code.

propertyLlama-3.1-8Bgpt-oss-20B
attention patternuniform full attention ×32alternating: 12 sliding-window (128 tok) + 12 full
FFNdenseMixture of Experts — 32 experts, top-4
softmaxstandardlearned attention sinks
head_dim12864
KV cacheone uniform poolhybrid — quantized + bf16 side by side

Hybrid attention is the consequential one. Half of gpt-oss's layers see only the last 128 tokens, so quantizing them is pointless — only the 12 full-attention layers are compressed. That demands a wrapper pool routing per layer, a dual allocator, index translation between pools, and a dense re-indexing mapping global layer ids [1,3,…,23] onto the 12-entry calibration bundle.

Learned sinks add a per-head constant to the softmax denominator, letting a head attend to "nothing". They had to be threaded into the quantized decode kernel and, for prefill, applied as an exact rescale of a sink-less output, o · sigmoid(lse − sink).

MoE means each token's FFN is selected discretely by a router — which turns out to matter enormously.

The earlier inference that they excluded every engine fault because vq2 passed the same short sweeps was too broad: vq2 shares the quantized prefill path, where a separate concurrency-dependent bug was later reproduced.

A separate engine bug: piecewise prefill graph padding

The later crash required sampled decoding (temperature=1) and concurrent long prompts. Greedy decoding silently hid the non-finite logits by using argmax; the sampled path exposed them when torch.multinomial rejected its probability tensor.

PiecewiseCudaGraphRunner rounds a real prefill count up to a captured bucket and pads q/k/v. The custom _forward_extend_quantized_dense path passed that padded q to FlashAttention while cu_seqlens_q still described only real requests. The required invariant cu_seqlens_q[-1] == q.shape[0] was false.

The caller declared no sequence covering the trailing rows, so FlashAttention was not required to define them. Probes found exactly that padding footprint non-finite: 3×32×64 = 6144 values for 1→4, 5×32×64 = 10240 for 283→288 and 12×32×64 = 24576 for 68→80.

Fixing only that call was insufficient. An isolated dummy sequence made the quantized full-attention result finite, but the intervening bf16 sliding-window backend again left metadata-excluded padding rows undefined. Captured residual and MoE segments then propagated them. GPT-OSS makes this reliably fatal because its learned-sink correction consumes attention LSE and its MoE computation processes padded token rows.

False graph control DISABLE_CUDA_GRAPH=1 disabled decode graphs only. The supposedly graphs-off failure had disable_cuda_graph=True but disable_piecewise_cuda_graph=False; prefill replay was still captured.

This affects vq2 as well as plain INT2. --vq2 still sets kv_cache_dtype=int2; its codebook changes the K tier, while V stays INT2 and both modes share the quantized prefill implementation.

This is an integration-layer bug, not a FlashAttention implementation bug. FlashAttention is a stateless kernel: it receives Q/K/V and cumulative sequence offsets, and cannot infer whether rows omitted from those offsets are graph padding, another request or invalid input. The SGLang/OSCAR adapter owns that tensor-to-metadata contract and the lifetime of static graph buffers, so the repair belongs at that boundary; no FlashAttention code is changed.

Disabling piecewise prefill, or eagerly running only non-exact tails, avoids the bug but gives up the launch-overhead reduction needed for a fair throughput comparison. The production fix preserves padded replay with two invariants. First, it appends an isolated zero-Q/K/V dummy sequence for the rounded rows and extends both query and KV indptrs, restoring cu_seqlens_q[-1] == q.shape[0]. Second, the shared attention boundary zeros rows beyond the real token count after every backend, containing padding across alternating quantized full-attention and bf16 sliding-window layers.

The exact 24-row, four-thread sampled VQ2 regression completed 24/24 in 44 s with both decode and piecewise prefill graphs enabled. All 69 logged prefill launches reported cuda graph: True, including 72-, 80-, 144- and 288-token ragged totals and all 48 bulk 4096-token chunks; every decode launch was graphed.

The same full-graph scalar-INT2 regression completed 24/24 in 45 s. All 55 prefill launches were graphed, including 288- and 296-token ragged totals, every decode launch was graphed, and neither mode produced a scheduler exception or sampler assertion. INT2 nevertheless scored 0.0 and every row reached the 256-token cap, independently confirming that serving correctness and scalar-INT2 fidelity are separate. Sampled completion lengths make these figures validation of the fast path, not a controlled benchmark. The earlier exact-size guard and all-eager runs were diagnostic controls, not the final execution policy.

A final pre-commit VQ2 rerun exposed and then closed a separate hybrid-SWA allocator leak. The HP-recent ring had 263 slots (256 + N_Q - 1), but decode allocates its next HP slot before the flush plan releases the oldest N_Q=8 slots. On the first wrap, the new full→SWA mapping overwrote slot 0's still-live mapping; the flush then freed the new mapping and permanently lost the old SWA slot.

The ring bug is not specific to GPT-OSS, nor is it owned by an attention kernel. It requires the mixed HP+quantized cache, the SWAKVPool full-slot-to-SWA-slot mapping, and a request long enough to wrap the recent-HP ring. GPT-OSS exposes that combination reliably because it alternates full and sliding-window attention layers. Dense full-attention models have no SWA mapping and cannot suffer this particular mapping leak; any other hybrid-attention model using the same cache configuration could. Scalar INT2 and vq2 are both covered because they share this allocator and lifecycle. FlashAttention only consumes the resulting KV tensors and indices; it does not allocate SWA slots, maintain mappings or recycle request state.

The ring now reserves the transient allocation slot (256 + N_Q = 264), and the hybrid wrapper delegates release_req_slab. With strict idle memory checking enabled, a sampled 24-row run scored 75.0 with 12 wrap crossings; a second fixed-length run forced all 24 requests across the boundary and scored 91.67. Across both runs, all 126 prefill launches were graphed (30 ragged tails), the server remained healthy after returning to idle, and there was no allocator leak, scheduler exception or non-finite diagnostic.

Controlled throughput: no VQ2 speedup at 8K

The sampled regression timings cannot compare methods because completion lengths differ. A controlled run used the same 24 NIAH-8K prompts (198,250 prompt tokens per run), concurrency four, greedy decoding with EOS ignored, and exactly 256 output tokens per request (6,144 total). All arms used TP=2 on the same A100-40GB pair, Triton attention, both CUDA graph mechanisms, and the same decode split-K factor of 48. At this operating point, scalar INT2 is 20.1% slower than bf16 and VQ2 is 28.3% slower than bf16 and 10.3% slower than scalar INT2. The integrated VQ2 path has more total overhead than the KV bandwidth it saves at 8K, but this run does not identify the fused VQ gather as that overhead: isolated stage-1 measurements below show that it is already competitive with scalar INT2. --triton-attention-num-kv-splits controls how many KV-length partitions produce partial attention results before a final reduction. More splits expose parallelism but add partial-buffer and reduction overhead. The launcher previously defaulted VQ2 to 48 and INT2/bf16 to 8 because their kernel-specific optima differ. That is a valid best-tuned-system comparison when labeled, but it cannot by itself attribute a speedup to the codec; this table deliberately matches the split count.

Performance audit: graph-fix cost and VQ2 optimization

The padded-graph repair has a nonzero but small cost, only on ragged piecewise-prefill replay. Exact-size buckets take the false branch and launch no repair GPU work. For ragged buckets the defensive path clones and clears padded Q, creates zero dummy K/V rows, extends the indptr, executes a small isolated dummy sequence, and clears padded attention output rows.

An A100 operation-level reproduction of the newly added tensor operations, excluding K/V concatenations that already existed, measured 3.27–3.66 ms per ragged prefill batch across the observed 1→4, 68→80 and 283→288 shapes. This is not a server A/B and excludes the dummy sequence's FlashAttention increment, but that increment covers only 3–12 zero tokens here. The controlled VQ2 run had 48 exact 4096-token chunks and about 21 ragged launches over roughly 46.6 s: about 71 ms, or ~0.15% of wall time, before the small dummy-attention increment. The repair cannot explain VQ2's 10.3% gap to INT2.

The clearest implementation target is one fused Triton nearest-codeword writer shared by prefill and decode flush. Both paths currently normalize in fp32, materialize [T,H,NG,256] scores through torch.einsum, then launch separate subtraction, argmax, cast, scale allocation and scatter operations. A fused reduction can write the uint8 index and per-token scale directly and mask invalid flush-plan rows, removing the 128 MiB prefill temporary without changing the codec.

Second, _vq_prefix_dequantize_k expands uint8 indices to int64, reconstructs codewords through advanced indexing, gathers HP rows even for quantized slots, and then selects with torch.where. Scalar INT2 already performs the analogous mixed HP/quant operation in one Triton kernel. A VQ counterpart is straightforward, although its isolated cost makes it less urgent than the encoder.

Third, the split cap needs an end-to-end sweep instead of a fixed VQ2 default of 48. Unified stage 2 uses TOTAL_SPLITS as a compile-time loop bound and scans every configured HP+quant scratch slot. Isolated VQ2 stage 1 was effectively tied at split 16 and 48 for this 8K shape (143.35 vs 142.75 µs/layer), so 48 may add reduction work for almost no stage-1 gain. A served split-16 attempt before the ring fix terminated after eight requests. After the fix, the same configuration completed a strict fixed-length 24/24 correctness run, scored 95.83, and graphed all 57 prefills without a leak. Its single 146.93 tok/s observation is not a tuned or repeated benchmark, so the split-count performance question remains open.

Lower-priority graph-repair cleanup could zero only padded views instead of cloning Q, cache the extended query indptr once per forward, and move the dummy request into shared PCG attention metadata. The measured 8K ceiling for those changes is only on the order of tenths of a percent, and the sampled 24-row regression must remain the correctness gate.

Quantizing the sliding-window layers is harmless; damage scales with the number of full-attention layers quantized. The structural reading: gpt-oss's window layers see only 128 tokens, so the 12 full-attention layers are the sole channel for long-range information, with no redundancy to average quantization noise against. Llama spreads the same information across 32 full-attention layers, any one of which can compensate for another.

At the first quantized layer both models receive identical inputs — gpt-oss's layer 0 is a sliding-window layer with an unquantized cache, and its measured drift is exactly 0.000. Same queries, only the KV quantized. And gpt-oss's attention output comes back fully decorrelated (drift above 1.0) where Llama's is off by 15%.

From there it compounds. gpt-oss reaches 0.890 at the output layer — the residual stream is essentially unrelated to the true one, which is precisely the word salad observed. Llama saturates near 0.39.

82% of all expert-routing decisions flip between the two runs, rising to 97.9% at the final layer. Each flip swaps an entire FFN — a discrete amplification channel a dense model structurally lacks.

07What this means for the project

  • vq2's codec result survives, but vq2 was not unaffected. Sampled concurrent serving hit the shared graph-padding bug. The fixed engine now executes both bulk chunks and ragged quantized-prefill tails through piecewise graphs.
  • The codec result is stronger than the Llama grid shows. Scalar INT2 fails outright in the engine-free simulation while vq2 holds in graph-safe quality sweeps — a clean separation after excluding graph-corrupted runs.
  • VQ2 currently has no demonstrated 8K throughput win on gpt-oss/A100. Under matched split 48, bf16 is 39.5% faster than VQ2 and scalar INT2 is 11.4% faster. Longer-context and split-count sweeps are required before making a tok/s speedup claim.
  • There is currently no meaningful scalar-INT2 baseline on gpt-oss. The corrected padded graph path restores serving correctness, but it does not repair the independently reproduced scalar-INT2 quality collapse.
  • The natural follow-up is a fidelity-threshold framing: measure vq2's reconstruction on the same tensors, turning "vq2 is better" into "gpt-oss requires ≥X fidelity; INT2 delivers 0.92, vq2 delivers Y."

08Confidence and caveats

Solid. There are two independent findings. The scalar-INT2 quality collapse reproduces with zero engine code while the Llama HF control stays 10/10 → 10/10. Separately, the served NaN localizes to padded quantized prefill, its count exactly matches the padding footprint, the all-eager and exact-size controls pass, and the final padded-replay fix passes the same sampled concurrency regression under both VQ2 and scalar INT2 with every logged prefill and decode launch graphed.

Suggestive, underpowered. The dose-response and the window-vs-full-attention split are n=10 at a single 1064-token setting. bf16 itself scores only 4/10 there, because the reconstructed prompts are hard and the 96-token cap truncates gpt-oss's reasoning — so headroom is small. Directionally clear, not publishable as-is.

The throughput comparison is also only two warmed runs per arm at one context length, concurrency and split count. Its ordering is consistent across both runs and is sufficient to reject an 8K speedup claim, but it is not a complete performance characterization.

Not established. Why gpt-oss's attention output decorrelates at the first quantized layer given better KV fidelity. Attention sinks are the leading suspect — sink-dominated heads leave little softmax mass on content, so a perturbation is relatively larger — but this was not isolated. The 82% expert-flip rate is consistent with MoE amplification but does not separate cause from consequence; flips could be downstream of an already-large drift. The clean test is a matched-noise control: inject random KV noise into Llama at a magnitude producing drift 1.2 at layer 1, and see whether Llama also collapses.

Process note Several probes produced instrumentation errors, and one control was interpreted too broadly. Most consequentially, DISABLE_CUDA_GRAPH=1 was labeled “graphs off” even though piecewise prefill graphs remained enabled. Any single measurement here should be treated as provisional until it reproduces both a passing and a failing case.
