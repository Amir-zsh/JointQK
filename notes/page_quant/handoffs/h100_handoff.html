1What this project is

We compress the transformer KV cache at serving time to ~2 bits/element and measure what survives. The flagship method, vq2, is a group-vector-quantized K tier inside the OSCAR serving engine (a research sglang fork): keys are mapped per (layer, KV-head) into a calibrated basis, split into 16 groups of 4 dims, and each group stored as one uint8 index into a 256-entry codebook plus a per-token fp8 RMS scale; V stays on OSCAR's scalar-INT2 path. Everything — quantize-on-aging behind a bf16 sink+recent band, fused triton decode kernels, chunked-prefill dequant — runs inside one engine, so every method is compared served, not offline. Baselines in the same stack: OSCAR-INT2 (production release: calibrated rotations + percentile clips), TurboQuant-INT2 (Lloyd-Max, calibration-free), QuaRot-INT2, Naive-INT2, and the bf16 ceiling.

Headline results so far: vq2 holds long-context retrieval where scalar INT2 collapses (Llama-3.1-8B 64K NIAH: 92 vs 77; Qwen3-8B: 77 vs 23), is context-flat at ~7 pts below bf16, decodes 12–13% faster than OSCAR-INT2 at 100K on A100, and the sharpest design law we've measured: codebook calibration must cover the serving position range — a 64K-calibrated codebook serves 131K at 0.16 (total collapse) while a 128K-calibrated one serves it at 68.2. gpqacc128k (4 × 131,072-token concat) is now the canonical calibration everywhere.

3How to run experiments

Everything eval flows through the declarative layer — one JSON spec per study, full provenance per run:

# 1. spec: pipelines/oscar_e2e/experiments/<study>.json
#    (model, per-method serve_args+env+calibration paths, cells with rows/shards/sampling)
.venv/bin/python pipelines/oscar_e2e/run_experiment.py \
    --spec pipelines/oscar_e2e/experiments/llama31_8b_vq2_128k.json \
    --queue logs/queue.tsv
# -> experiment_manifest.json (git SHAs, artifact sha256s), arms/*.sh, sharded queue

# 2. one pool worker per GPU (ARMS_DIR = spec mode)
for g in 0 1 2 3; do ARMS_DIR=$PWD/<out_root>/arms \
  nohup bash pipelines/oscar_e2e/gpu_pool_runner.sh logs/queue.tsv $g & done

# 3. merge + score when no TODO/RUN rows remain
.venv/bin/python pipelines/oscar_e2e/merge_shards.py --root <out_root>

Serving directly (smokes, TP, one-offs): pipelines/oscar_e2e/serve_oscar.sh — modes --bf16 / (int2 default) / --vq2 --vq-codebook <bundle> / --int2plain; env knobs: ROT_DIR (rotations), TP, MAX_TOKENS (pool), HADAMARD_ORDER + SGLANG_LLOYD_MAX=1 (TurboQuant), SGLANG_INT2_NO_HADAMARD=1 (Naive), SGLANG_VQ_V_CODEBOOK_PATH (VQ-V ablation). Gates before trusting any new build: verify_vq_engine.py (G1–G6) and verify_turbo_lm.py (T1–T4) — expected outputs are in the team handoff. Protocol per cell type (rollouts, caps, scorers) is spelled out in Report 12 §0.

New-model onboarding checklist (the distilled recipe)

  1. Config check: layer_types (any sliding-window layers? → calibrate/quantize full-attention layers only, cf. gpt-oss), head_dim, KV heads, rope_scaling (native vs YaRN — decides position-coverage risk), native max positions.
  2. Rows: export with the model's own chat template AND tokenizer-budgeted context (assert max prompt + gen cap ≤ native window over ALL rows — sampling every Nth row missed overflows twice).
  3. Calibration: 198-prompt GPQA corpus, both deliveries — per-prompt dump → rotations (authors' pipeline, model's head_dim); 4×131072 concat → codebook (gpqacc128k recipe). Copy a build_*.sh (gated stages, heartbeat, idempotent).
  4. Short-val BEFORE full cells: extraction works, cap-hit ≤15%, thinking models close their think block, and sampling params from the model card (gpt-oss NEEDS T=1.0 — greedy degenerates into loops; R1-distill T=0.6/top-p 0.95; Llama T=0.6/top-p 0.9).
  5. Sanity: NIAH scores must decrease with context. A rising curve means protocol artifact, not a discovery — this check has caught two real bugs.

4H100-specific: kernels and dtypes

fp8 codebook format — the one real dtype decision. Codebook centroids are packed 4-per-int32 as fp8-e5m2 solely because sm80 Triton can only bitcast fp8e5. H100 (sm90) bitcasts e4m3 too, which has an extra mantissa bit — measurably better centroids (the e5m2 snap costs +3.3% reconstruction MSE on V, less on K). Recommendation: keep e5m2 first so H100 numbers are directly comparable to the A100 record, then A/B e4m3 as a clean upgrade: regenerate bundles with make_fp8.py --fmt e4m3 and switch the bitcast dtype in the vq2 decode kernel (decode_attention.py, fp8e5 → fp8e4nv) + the loader's snap (vq_codebook.py). Both sides must switch together — encoder assigns against the snapped centroids the decoder reconstructs (the encode/decode-same-bytes invariant).
  • Triton launch configs are A100-tuned: vq2 decode uses BLOCK_N=128 / 4 warps / 3 stages, and split-K is per-method (48 vq2 / 8 others). H100's SM count and shared memory differ — retune before any throughput claim, and keep the project rule: always compare methods at matched split-K and identical backend settings.
  • Attention backends: quantized paths exist only in the triton backend — keep --prefill/decode-attention-backend triton for every quantized configuration. On H100, FA3 becomes available for bf16; if you use it for the bf16 ceiling, report it as a separate "best-effort bf16" row — the apples-to-apples bf16 reference for kernel comparisons stays triton.
  • MXFP4 (gpt-oss): sm90 serves the native MXFP4 checkpoint (openai/gpt-oss-20b) — no more BF16-dequant, weights drop 42→~13GB, single GPU. But our A100 bf16 record used unsloth/gpt-oss-20b-BF16; MXFP4-native and bf16-dequant are not bit-identical models. Pick one per study and record it in the spec's calibration/model fields.
  • Memory geometry changes: 80GB HBM removes most TP requirements — Llama/R1D at 131K fits ONE H100 (34GB KV + 16GB weights), gpt-oss bf16 fits one card. TP=2 remains only for throughput studies or bigger models. The TP support (rank-sharded codebooks, clone 0ecb1ab7c) works as-is; the expandable_segments↔custom-all-reduce conflict (vllm#42609) is architecture-independent — serve_oscar.sh already drops expandable segments under TP>1, keep that behavior.
  • Throughput protocol (matching the existing Table-3 record): bs=1 streaming inter-token latency, ms/token, median of 3 reps, contexts 30/60/100K (+131K now feasible), CUDA graphs on. A100 record to beat/compare: vq2 1.7–1.8× over bf16 and 12–13% over OSCAR-INT2 at 100K. Expect H100 to compress these gaps for bandwidth-bound paths (HBM3 vs HBM2e) and re-tune before concluding anything.

5Calibration: approach, and how to speed it up safely

The invariants (don't trade these for speed):

  • One corpus per model — the 198 GPQA-Diamond prompts (artifacts/prompt_rows/gpqa_diamond.csv) feed rotations AND codebooks; measured provenance effects are ~1 pt, but mixed provenance is unfalsifiable noise in comparisons.
  • Position coverage = max serving context. The cliff is real (0.16 vs 68.2 at 131K) and governed by post-RoPE angular coverage: native-RoPE models extrapolating past calibration collapse; YaRN-interpolated serving is protected. Concat length ≥ serving max is free insurance — 4×131072 costs the same 524K-token budget as 8×65536.
  • fp64 (or compensated) second moments. Moments accumulate over 524K tokens; naive fp32 outer-product sums can distort the eigenstructure that rotations/codebooks are built from.
  • Model-authentic capture: model's own chat template, own weights (never reuse a base model's artifacts for a fine-tune — R1-distill showed the fine-tune reshapes K statistics), sink-correct attention where sinks exist.

Speedups that don't touch accuracy. Cost is model-path dependent: the Llama-family capture (capture_mixed_concat.py, flash/sdpa prefill, on-GPU fp64 accumulators) is already fast — measured 8 min for the full 4×131K R1D capture on 3×A100 — so don't spend effort there. The slow path is the gpt-oss-style HF capture (~30 min/128K sequence on A100; profile: eager+chunked attention ≳ fp64 moment einsums ≳ CPU-hook PCIe roundtrips ≫ rest). Items below target that path:

  1. H100 for free: fp64 is ~3.5× A100, HBM3 transfers ~2×, and HF capture can use flash kernels (H100 has the sink-aware FA3-family kernel, so gpt-oss's eager+512-chunk workaround disappears — plain fast forwards). Expect 3–5× just from hardware.
  2. Kill the CPU roundtrip: the hooks assemble Q on the host and the accumulator ships chunks back (~120GB PCIe per 128K sequence). Accumulate moments directly from GPU-resident hook chunks — ~2× on top.
  3. Parallelize sequences across GPUs: the 4 concat sequences are independent — one per GPU, merge partial moments at the end (they're sums). Near-linear.
  4. Two-pass precision: fp32/TF32 einsum per 4K chunk + fp64 reduction across chunks retains effectively fp64 stability at tensor-core speed — validate once against the fp64 reference (moment cosine + downstream gate ratio) before adopting.
  5. Longer-term: capture through the sglang engine itself (taps at forward_extend; design + TP shard-reassembly notes in the team handoff discussion) — same-numerics-as-serving AND fastest, but it's a project, not a tweak.

What NOT to shrink: corpus size, token budget, pool sampling (pool-stride 4), or position coverage — these are the accuracy-bearing quantities. All measured speedup headroom is in the compute path.

6Things that will bite you (each of these cost us hours)

traprule
Every reader/writer of a storage format is its own correctness surfaceThree separate incidents (VQ-V prefix dequant; TurboQuant's two writers; SWAKVPool signature). After touching any pool/kernel, run the full gate battery, and grep for OTHER implementers of the same interface.
Impossible curves = protocol bugsNIAH rising with context caught the char-wise scoring bug and the gpt-oss greedy collapse. Check monotonicity before believing any number.
Long-generation capacity race (tracker r1d-1)Admission control vs quant-page flush disagree near pool capacity under many 32K-cap requests. Bound concurrency: threads ≈ pool_tokens / (prompt+cap); POOL_MAX_REQS=4 for 32K caps at a 140K pool. Engine-level fix is open backlog.
Duplicate GPU ordinal → silent CPU fallback (tracker r1d-2)CUDA_VISIBLE_DEVICES=1,2,2 fails CUDA init (Error 101) and device_map="auto" silently places the model on CPU — the job runs ~50× slow forever and GPU-scoped kill-sweeps never see it. Dedupe GPU lists before export and fail fast on torch.cuda.is_available() in every capture/build launcher (fixed in build_r1d_128k.sh, commit 046954a — pull ≥ this).
Hybrid-SWA input-length capsglang limits input to the SWA pool size (0.8 × MAX_TOKENS). For 131K prompts on SWA models set MAX_TOKENS=168000.
Rented-node multi-tenancy (if shared)One orchestrator, serial lanes, single owner of GPU kill-sweeps (a concurrent sweep killed our own capture), generous boot timeouts, never kill by name — only by PID+UUID+owner.
torch.save of strided viewsPersists the full backing storage (4× pool bloat). .contiguous() before saving.
ConventionsLayer-0 excluded from headline offline stats; pre-merge .pre_<fix> backups before overwriting canonical artifacts; bugs → notes/page_quant/fixes_to_apply.md (bugs only); every long run: log + heartbeat + idempotent resume.
